Rust src/main.rs 完整語法與程式設計解析

main.rs 是一個使用 Rust 開發的 MP3 / FLAC 多裝置同步音樂播放器。此一音樂播放程式整合了 Windows 系統音量控制、串流解碼、10 段參數式等化器（PEQ）、多個音訊輸出裝置同步播放、播放定位，以及多種 GUI 色彩主題。

以 Rust 學習與實際軟體工程的角度來解說：

  1. Rust 的語法、型別、所有權與借用。
  2. 各種 struct、impl、trait 的設計目的。
  3. Arc、AtomicBool、AtomicUsize 等多執行緒共享資料的原理。
  4. 音訊解碼、串流播放與數位訊號處理的實作。
  5. egui 的 GUI 事件處理與畫面更新機制。
  6. 整個程式的架構、資料流與設計優缺點。

這份程式相當適合作為 Rust 中階到進階的學習教材，因為它同時使用了泛型、Trait Object、閉包、迭代器、錯誤處理、智慧指標、原子變數及非同步音訊播放架構。

2.1 use 是什麼？

use 的作用是將其他模組中的型別、函式或 Trait 引入目前的作用範圍。

例如：

use std::fs::File;

之後就可以直接使用：

let file = File::open("music.mp3");

而不用每次都寫：

let file = std::fs::File::open("music.mp3");

這和 Python 的：

from pathlib import Path import ...

概念類似，但 Rust 的模組與型別系統更加嚴格。

2.2 {} 是什麼？

例如：

use std::path::{Path, PathBuf};

代表一次引入同一個模組中的多個名稱。

等同於：

use std::path::Path;
use std::path::PathBuf;

2.3 self 的作用

use eframe::egui::{self, Color32, RichText, Vec2};

這裡的 self 代表引入 egui 模組本身。

所以後面可以混合使用：

egui::CentralPanel
Color32
RichText
Vec2

這是一種很常見的 Rust 寫法。

三、Windows 系統音量控制：COM 與 unsafe

原始程式第 14–95 行。

這是整份程式中比較特殊的部分，因為它不使用 rodio 控制音量，而是直接透過 Windows API 修改作業系統的預設播放裝置音量。

3.1 為什麼要區分兩種音量？

本程式有兩種不同的音量概念：

音量 控制對象 作用
Windows Endpoint Volume Windows 預設播放端點 影響使用該裝置的其他程式
rodio Sink Volume 播放器中的單一音訊串流 只影響本播放器的該個輸出

例如：

假設 Windows 預設喇叭音量是 80%，而播放器中的某個 Sink 音量是 50%。

實際輸出會同時受到兩層音量控制。

因此，兩者不能混為一談。

3.2 #[cfg(windows)]

#[cfg(windows)]
fn get_windows_endpoint_volume() -> anyhow::Result<f32> {

cfg 是 Rust 的條件編譯屬性。

這表示：

只有在 Windows 平台編譯時，才會編譯這個函式。

相反地：

#[cfg(not(windows))]
fn get_windows_endpoint_volume() -> anyhow::Result<f32> {
    anyhow::bail!("Windows 音效端點音量控制僅支援 Windows")
}

表示在非 Windows 平台，使用另一個同名函式。

這種設計的好處是：

  • Windows 可以直接控制系統音量。
  • Linux、macOS 仍然可以編譯其他播放器功能。
  • 不需要在執行期間才判斷作業系統。

這稱為 Conditional Compilation。

3.3 anyhow::Result<f32> 是什麼？

這是 Rust 常見的錯誤回傳型別。

它相當於：

Result<f32, anyhow::Error>

Rust 的 Result 有兩種可能：

Ok(value)
Err(error)

例如：

Ok(0.85)

表示成功讀取音量，數值是 85%。

而：

Err(error)

表示執行過程發生錯誤。

為什麼不直接回傳 f32？

因為 COM 初始化、取得音訊裝置、呼叫 Windows API 都可能失敗。

使用 Result 可以讓呼叫者知道是否成功，而不必用特殊數值表示錯誤。

3.4 unsafe 的用途

unsafe {
    let hr = CoInitializeEx(None, COINIT_MULTITHREADED);
}

Rust 預設會檢查記憶體安全性。

但是 Windows COM API 有一些操作需要呼叫者承擔額外的安全責任，因此部分介面被放在 unsafe 區塊中。

unsafe 並不表示這段程式一定不安全。

它的意思是：

編譯器無法完全證明這些操作符合安全條件，必須由程式設計者負責。

3.5 COM 初始化與 HRESULT

let hr = CoInitializeEx(None, COINIT_MULTITHREADED);

這裡使用 Windows COM 的多執行緒 Apartment 模型。

接著：

let initialized = if hr.0 >= 0 {
    true
} else if hr.0 == 0x8001_0106u32 as i32 {
    false
} else {
    return Err(anyhow::anyhow!(
        "COM 初始化失敗，HRESULT：0x{:08X}",
        hr.0 as u32
    ));
};

這裡有幾個值得學習的語法。

第一：hr.0

hr 是 HRESULT 型別的值，而 .0 表示存取其第一個 tuple 欄位。

第二：as i32

型別轉換。

第三：{:08X}

格式化輸出：

  • X：十六進位大寫。
  • 8：至少八個字元。
  • 0：不足八位時前面補零。

第四：return Err(...)

立即結束函式，回傳錯誤。

3.6 閉包 ||

let result = (|| -> anyhow::Result<f32> {
    let enumerator =
        CoCreateInstance::<_, IMMDeviceEnumerator>(
            &MMDeviceEnumerator,
            None,
            CLSCTX_ALL
        )?;

    let device =
        enumerator.GetDefaultAudioEndpoint(eRender, eMultimedia)?;

    let endpoint: IAudioEndpointVolume =
        device.Activate::<IAudioEndpointVolume>(CLSCTX_ALL, None)?;

    Ok(endpoint.GetMasterVolumeLevelScalar()?.clamp(0.0, 1.0))
})();

這是一個非常值得理解的 Rust 語法。

|| 表示不接受任何參數的閉包。

例如：

let f = || {
    println!("Hello");
};

f();

這裡的寫法：

(|| -> anyhow::Result<f32> {
    // ...
})()

分成兩個動作：

  1. 建立一個閉包。
  2. 立即呼叫這個閉包。

為什麼要這樣設計？

因為閉包內部使用了 ?，可以讓多個 Windows API 錯誤自動傳回 Result。

但是，閉包結束後，外層仍然能執行：

if initialized {
    CoUninitialize();
}

這樣就能確保 COM 的初始化與解除初始化有明確的生命週期。

這是一種將錯誤處理與資源清理分離的設計方式。

3.7 ? 運算子

例如：

let device = enumerator.GetDefaultAudioEndpoint(eRender, eMultimedia)?;

? 的意思是：

  • 如果結果是 Ok(value)，取出 value 繼續執行。
  • 如果結果是 Err(error)，立即回傳錯誤。

相當於：

let device = match enumerator.GetDefaultAudioEndpoint(eRender, eMultimedia) {
    Ok(value) => value,
    Err(error) => return Err(error.into()),
};

? 是 Rust 非常重要的語法，建議熟練掌握。

4.4 #[derive(Clone, Copy)]

這個屬性讓 Rust 自動實作兩個 Trait。

  • Clone：允許明確複製。
  • Copy：允許以複製方式傳遞，而不移轉所有權。

因為 Color32 本身是適合複製的小型資料，所以這種設計很合適。

4.5 match 表達式

fn theme_palette(index: usize) -> ThemePalette {
    match index % THEME_NAMES.len() {
        1 => ThemePalette { /* ... */ },
        2 => ThemePalette { /* ... */ },
        3 => ThemePalette { /* ... */ },
        4 => ThemePalette { /* ... */ },
        _ => ThemePalette { /* ... */ },
    }
}

這是 Rust 的模式比對。

match 和其他語言的 switch 有點類似，但 Rust 的 match 是表達式，可以產生值。

這裡：

index % THEME_NAMES.len()

利用取餘數的方式確保索引落在 0–4。

_ 是萬用模式，代表其他所有情況。

let rgb = |r, g, b| Color32::from_rgb(r, g, b);

這是一個閉包。

它等同於建立一個簡化的 RGB 轉換函式。

所以：

比：

fn apply_theme(ctx: &egui::Context, index: usize) {
    let p = theme_palette(index);
    let light = index % THEME_NAMES.len() == 4;

    let mut visuals = if light {
        egui::Visuals::light()

這段展示了 Rust 的幾個特性：

五、PlayingDevice：如何管理多個音訊輸出裝置

原始程式第 203–258 行。

5.1 PlayingDevice 結構體

struct PlayingDevice {
    name: String,
    _stream: OutputStream,
    sink: Sink,
    volume: f32,
}

這個結構體代表一個正在播放音訊的輸出裝置。

逐項說明：

欄位 型別 用途
name String 裝置名稱
_stream OutputStream 維持音訊輸出串流
sink Sink 控制該裝置的播放
volume f32 該裝置的獨立音量

其中最值得注意的是：

_stream: OutputStream

為什麼前面有底線？

Rust 通常會對未使用的變數提出警告。

但是這個欄位雖然沒有直接被程式讀取，卻有非常重要的作用：維持音訊串流的生命週期。

如果 OutputStream 被釋放，底層音訊輸出可能就會停止。

因此，即使不直接使用它，也必須將它保存在 PlayingDevice 中。

這是 Rust 中非常重要的資源管理觀念：

物件的存在時間必須涵蓋它所管理的資源需要運作的時間。

5.2 Biquad：數位音訊濾波器

#[derive(Clone)]
struct Biquad {
    b0: f32,
    b1: f32,
    b2: f32,
    a1: f32,
    a2: f32,
    z1: f32,
    z2: f32,
}

這是一個二階數位濾波器。

它不是單純調整音量，而是透過數學運算改變特定頻率的響應。

Biquad 是音響 EQ、低通濾波器、高通濾波器及音效處理中非常常見的基本單元。

其數學原理

二階 IIR 濾波器的差分方程式為：

\[ y[n]=b_0x[n]+b_1x[n-1]+b_2x[n-2] -a_1y[n-1]-a_2y[n-2] \]

其中：

  • \(x[n]\)：目前輸入的音訊樣本。
  • \(y[n]\)：目前輸出的音訊樣本。
  • \(b_0,b_1,b_2\)：前饋係數。
  • \(a_1,a_2\)：回授係數。

z1、z2 則是用來保存濾波器過去的運算狀態。

Default 實作

impl Default for Biquad {
    fn default() -> Self {
        Self {
            b0: 1.0,
            b1: 0.0,
            b2: 0.0,
            a1: 0.0,
            a2: 0.0,
            z1: 0.0,
            z2: 0.0,
        }
    }
}

這裡使用：

impl Default for Biquad

表示為 Biquad 實作 Rust 的 Default Trait。

因此可以使用：

let filter = Biquad::default();

這組初始係數代表：

\[ y[n]=x[n] \]

也就是沒有任何濾波效果，原音直接通過。

set_peaking()：設定 EQ 頻帶

fn set_peaking(
    &mut self,
    sample_rate: f32,
    frequency: f32,
    q: f32,
    gain_db: f32
)

這個函式用來設定 Peaking EQ 的參數。

四個參數分別是：

參數 意義
&mut self 可修改目前濾波器
sample_rate 取樣率
frequency 中心頻率
q 品質因數，控制頻寬
gain_db 增益，單位 dB

例如：

filter.set_peaking(44100.0, 1000.0, 1.0, 6.0);

代表設定：

  • 取樣率 44.1 kHz。
  • 中心頻率 1000 Hz。
  • Q 值 1.0。
  • 增益 +6 dB。

重要數學運算

let a = 10.0_f32.powf(gain_db / 40.0);

這裡使用浮點數的 powf()，計算：

\[ A=10^{G/40} \]

其中 \(G\) 是增益 dB。

接著：

let w0 = 2.0 * PI * frequency / sample_rate;

換算成數位角頻率：

\[ \omega_0=\frac{2\pi f_0}{f_s} \]

這些公式來自 RBJ Audio EQ Cookbook。

之後程式利用 sin()、cos() 計算濾波器係數。

process()：實際處理音訊

#[inline]
fn process(&mut self, input: f32) -> f32 {
    let output = self.b0 * input + self.z1;

    self.z1 = self.b1 * input - self.a1 * output + self.z2;
    self.z2 = self.b2 * input - self.a2 * output;

    output
}

這裡採用 Transposed Direct Form II。

它的優點是可以用兩個狀態變數保存運算所需的歷史資料。

每次傳入一個音訊樣本，就回傳一個處理後的樣本。

#[inline] 是編譯器提示，希望將函式內嵌到呼叫位置，減少函式呼叫開銷。

不過是否真的內嵌，仍由編譯器決定。

設計上的重要觀念：

濾波器不能每處理一個樣本就重新建立。

因為 z1、z2 必須連續保留，才能產生正確的濾波效果。

所以每個頻道都需要自己的濾波器狀態。

六、音訊解碼：Decoder、Source 與 Trait Object

原始程式第 255–311 行。

這個部分是整份程式的核心之一。

6.1 為什麼使用串流解碼？

type StreamingDecoder = Box<dyn Source<Item = f32> + Send>;

先解釋這個型別別名。

type 可以替複雜型別取一個容易閱讀的名稱。

原本的型別是：

Box<dyn Source<Item = f32> + Send>

拆開來看：

語法 意義
Box<T> 在 Heap 配置資料的智慧指標
dyn Source 動態分派的 Trait Object
Item = f32 Source 輸出的項目型別是 f32
Send 可以安全地將物件移交至其他執行緒

為什麼使用 dyn Source？

rodio 的音訊來源可能是：

  • Decoder。
  • 取樣率轉換後的 Source。
  • 套用音效後的 Source。
  • 跳過指定時間後的 Source。

這些物件的具體型別可能不同，但都實作了 Source Trait。

因此不必在程式中為每種來源建立不同的型別處理邏輯。

可以統一使用：

Box<dyn Source<Item = f32> + Send>

這稱為 Trait Object。

靜態分派與動態分派

Rust 有兩種重要的多型實作方式。

方式 語法 特點
靜態分派 impl Trait、泛型 編譯期決定具體型別
動態分派 dyn Trait 執行期透過 Trait Object 呼叫

本程式使用動態分派，主要是為了讓不同音訊處理鏈可以統一存放在同一個欄位中。

6.2 open_audio_decoder()

fn open_audio_decoder(
    path: &Path
) -> anyhow::Result<Decoder<BufReader<File>>> {

這個函式負責開啟音樂檔案並建立解碼器。

注意參數：

path: &Path

這裡使用借用，而不是：

path: PathBuf

原因是函式只需要讀取路徑，不需要取得路徑的所有權。

Path 和 PathBuf 的差別

型別 特性
Path 借用形式的路徑
PathBuf 擁有資料的路徑

可以將它理解成：

  • Path 類似 str。
  • PathBuf 類似 String。

取得副檔名

let ext = path
    .extension()
    .and_then(|e| e.to_str())

七、GatedSource：整份程式最重要的設計

如果要真正理解這個播放器如何達成多裝置同步、即時 EQ 及同步跳轉，就必須理解 GatedSource。

7.1 先看它的結構

struct GatedSource {
    path: Arc<PathBuf>,
    inner: StreamingDecoder,

    start_gate: Arc<AtomicBool>,

    seek_target: Arc<AtomicUsize>,
    seek_generation: Arc<AtomicU64>,

    seen_seek_generation: u64,

    eq_gains: Arc<[AtomicU32; EQ_BANDS]>,
    last_gains: [f32; EQ_BANDS],

    filters: Vec<Vec<Biquad>>,

    channels: u16,
    sample_rate: u32,
    duration: Option<Duration>,

    cursor: usize,
    failed: bool,
}

這個結構體包含整個音訊串流的運作狀態。

可以分成五組：

分類 欄位 用途
音訊來源 path、inner 檔案路徑與解碼器
同步播放 start_gate 播放啟動閘門
跳轉控制 seek_target、seek_generation 同步定位
EQ 控制 eq_gains、last_gains、filters 即時等化
播放狀態 channels、sample_rate、cursor、failed 音訊資訊與錯誤狀態

7.2 Arc 是什麼？

這是 Rust 中非常重要的智慧指標。

Arc<PathBuf>

Arc 全名是：

Atomically Reference Counted

意思是原子參照計數。

假設同一個音檔要傳給三個輸出裝置：

                    PathBuf
                       |
                      Arc
                 _____|_____
                |     |     |
              裝置A  裝置B  裝置C

三個裝置可以共享同一個路徑資料。

不用複製三份 PathBuf 的內部字串資料。

Arc 和 Rc 的差別

型別 使用情境
Rc<T> 單執行緒共享
Arc<T> 多執行緒共享

因為音訊輸出可能由不同執行緒處理，因此本程式使用 Arc。

7.3 AtomicBool：播放啟動閘門

start_gate: Arc<AtomicBool>

這是非常巧妙的設計。

假設使用者同時選擇三個音訊輸出裝置。

如果每個裝置建立完成後就立即開始播放，可能會出現：

裝置 A：先播放
裝置 B：晚 20 ms 播放
裝置 C：晚 50 ms 播放

本程式的設計是：

先讓所有裝置建立 Sink，然後才一起開啟播放閘門。

在每個 GatedSource 中：

if !self.start_gate.load(Ordering::Acquire) {
    return Some(0.0);
}

意思是：

如果閘門尚未打開，就持續輸出數值為 0 的音訊樣本。

因此 Sink 可以先建立、預熱，而不會提前消耗真正的音訊內容。

所有裝置準備完成後：

self.start_gate.store(true, Ordering::Release);

這就是共同啟動閘門。

注意：這種方式可以減少各裝置啟動時的時間差，但不代表硬體層級的絕對同步。不同音訊裝置有各自的時鐘與緩衝區，長時間播放仍可能產生時鐘漂移。

7.4 Ordering：原子操作的記憶體順序

程式中有：

Ordering::Relaxed
Ordering::Acquire
Ordering::Release
Ordering::AcqRel

這些不是音訊功能，而是多執行緒記憶體同步機制。

Ordering 意義
Relaxed 只保證原子性，不建立跨變數同步順序
Acquire 確保後續讀取不越過這個讀取操作
Release 確保先前操作不越過這個寫入操作
AcqRel 同時具有 Acquire 和 Release 特性

例如：

self.start_gate.store(true, Ordering::Release);

以及：

self.start_gate.load(Ordering::Acquire);

配對使用可以建立跨執行緒的同步關係。

這樣音訊執行緒在看到啟動閘門打開時，也能看到啟動前已經發布的相關狀態。

7.5 AtomicUsize 和 AtomicU64：播放定位

seek_target: Arc<AtomicUsize>,
seek_generation: Arc<AtomicU64>,

這裡使用兩個變數，而不是只用一個。

用途不同：

  • seek_target：要跳轉到哪個音訊樣本位置。
  • seek_generation：是否出現新的跳轉命令。

例如：

目前 generation = 5
使用者拖曳進度條
target = 4410000
generation = 6

音訊執行緒看到 generation 從 5 變成 6，就知道需要執行新的定位。

這稱為 Generation Counter（世代計數器）。

比起持續輪詢整個 GUI 的狀態，這種方式更簡潔。

7.6 AtomicU32 如何儲存 f32？

這是另一個值得學習的 Rust 技巧。

eq_gains: Arc<[AtomicU32; EQ_BANDS]>

為什麼不用：

Arc<[AtomicF32; EQ_BANDS]>

因為標準 Rust 沒有提供通用的 AtomicF32。

因此程式使用：

gain.to_bits()

把 f32 的位元表示轉換成 u32。

讀取時：

f32::from_bits(...)

再轉換回浮點數。

例如：

let value = 6.0_f32;

let bits = value.to_bits();

let restored = f32::from_bits(bits);

restored 仍然是 6.0。

這種方式不會把浮點數轉換成整數數值，而是保留其位元表示。

7.7 Vec<Vec<Biquad>> 的意義

filters: Vec<Vec<Biquad>>,

這是二維動態陣列。

其結構為：

filters
  |
  +-- Channel 0
  |     +-- EQ 0
  |     +-- EQ 1
  |     +-- ...
  |     +-- EQ 9
  |
  +-- Channel 1
        +-- EQ 0
        +-- EQ 1
        +-- ...
        +-- EQ 9

例如立體聲：

左聲道：10 個 Biquad
右聲道：10 個 Biquad

因此：

vec![vec![Biquad::default(); EQ_BANDS]; channel_count]

就是建立每個聲道的 10 個獨立濾波器。

這非常重要。

如果左右聲道共用同一個濾波器狀態，左聲道的歷史樣本可能影響右聲道的濾波結果，造成錯誤。

為什麼使用 NaN？

7.9 refresh_eq()：更新 EQ

fn refresh_eq(&mut self) {
    for band in 0..EQ_BANDS {
        let gain = f32::from_bits(
            self.eq_gains[band].load(Ordering::Relaxed)
        );

        if (gain - self.last_gains[band]).abs() > 0.001
            || !self.last_gains[band].is_finite()
        {
            for channel_filters in &mut self.filters {
                channel_filters[band].set_peaking(
                    self.sample_rate as f32,
                    EQ_FREQUENCIES[band],
                    1.0,
                    gain,
                );
            }

            self.last_gains[band] = gain;
        }
    }
}

這段最重要的觀念是：

GUI 修改 EQ 時，不直接操作音訊執行緒中的濾波器，而是更新共享參數。

音訊執行緒自行讀取參數，並更新本地濾波器。

這是一種 Producer / Consumer 設計：

  • Producer：GUI，產生新的 EQ 參數。
  • Consumer：音訊來源，讀取 EQ 參數並處理音訊。

而且只有增益真正改變時，才重新計算係數。

這樣能減少不必要的運算。

7.10 apply_pending_seek()：同步跳轉

fn apply_pending_seek(&mut self) {
    let generation =
        self.seek_generation.load(Ordering::Acquire);

    if generation == self.seen_seek_generation {
        return;
    }

這裡比較目前的 generation 和上次處理的 generation。

如果相同，表示沒有新命令。

如果不同，就讀取：

let sample_index =
    self.seek_target.load(Ordering::Acquire);

接著將樣本位置轉換成秒數：

let seconds = sample_index as f64
    / self.sample_rate.max(1) as f64
    / self.channels.max(1) as f64;

這裡必須理解音訊樣本的排列方式。

假設：

  • 取樣率：44100 Hz。
  • 聲道數：2。
  • 目標樣本索引：441000。

那麼：

\[ t=\frac{441000}{44100\times2}=5 \]

即定位到約 5 秒。

為什麼除以聲道數？

因為程式使用的是交錯排列的音訊樣本：

左1、右1、左2、右2、左3、右3……

因此每秒總樣本數是：

\[ 44100\times2=88200 \]

接下來：

match open_stream_decoder(self.path.as_path(), target) {
    Ok(decoder) => {
        self.inner = decoder;
        self.cursor = sample_index;
        // ...
    }
    Err(error) => {
        eprintln!("音訊跳轉失敗：{error}");
        self.failed = true;
    }
}

成功時：

  1. 更換解碼器。
  2. 更新游標。
  3. 重設各濾波器的歷史狀態。
  4. 清除錯誤旗標。

為什麼重設 z1 和 z2？

因為跳轉後的音訊已經不是原本連續的時間序列。

若沿用跳轉前的濾波器狀態，可能產生不正確的瞬態響應。

7.11 Iterator Trait：讓音訊來源逐個輸出樣本

這是整份程式另一個非常重要的 Rust 語法。

impl Iterator for GatedSource {
    type Item = f32;

    fn next(&mut self) -> Option<Self::Item> {

表示：

為 GatedSource 實作 Iterator Trait。

type Item = f32 表示每次迭代產生一個 f32。

next() 的回傳值：

Option<f32>

有兩種可能：

  • Some(sample)：還有音訊樣本。
  • None：音訊串流結束。

真正的音訊處理流程

let channel = self.cursor % self.channels as usize;

if channel == 0 {
    self.refresh_eq();
}

let mut sample = self.inner.next()?;

for filter in &mut self.filters[channel] {
    sample = filter.process(sample);
}

self.cursor = self.cursor.saturating_add(1);

Some(sample)

逐步理解：

  1. 根據 cursor 判斷目前樣本屬於哪個聲道。
  2. 每次開始新的聲道組合時，檢查 EQ 是否更新。
  3. 從解碼器取得下一個音訊樣本。
  4. 依序通過該聲道的十個 Biquad。
  5. 增加樣本索引。
  6. 回傳處理後的樣本。

例如立體聲：

樣本 0 → 左聲道 → EQ 0~9
樣本 1 → 右聲道 → EQ 0~9
樣本 2 → 左聲道 → EQ 0~9
樣本 3 → 右聲道 → EQ 0~9

? 在 Iterator 中的意義

let mut sample = self.inner.next()?;

如果解碼器回傳：

Some(value)

就取得 value。

如果解碼器回傳：

None

則目前的 next() 也立即回傳 None。

因此整個音訊來源自然結束。

saturating_add()

self.cursor = self.cursor.saturating_add(1);

這是防止整數溢位的寫法。

一般的：

self.cursor += 1;

在極端情況下可能發生整數溢位。

saturating_add() 在超過型別上限時會停留在最大值。

對於長時間運作的音訊串流，這是較謹慎的寫法。
